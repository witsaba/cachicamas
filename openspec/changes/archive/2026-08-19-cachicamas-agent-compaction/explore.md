### The history/transcript store and AG-12's boundary validation entry point

`backend/agent/src/agent/history.go` (full file read):
- `History` (`:166-170`): unexported `entries []Entry`, `open []openCall`. **Append-only in the literal sense — there is no exported or unexported route to remove/rewrite/reorder an already-committed entry.** The single mutation primitive is `commit(op commitOp, ...)` (`:332-344`), dispatching to `commitAppendOp` (append validated by pairing rules) or `commitCloseTurnOp` (validates, mutates nothing).
- `NewSeededHistory(messages []ai.Message) (*History, error)` (`:216-224`) is the **de facto "boundary validation entry point"** the task description asks about — there is no separately named validator function. It re-runs the same append-time pairing rules over a fresh ordered message sequence, rejecting on the first orphaned result (`R-HIS-002`/`S-HIS-051`), and constructs entries with fresh ordinal-derived `EntryID`s. **Post-compaction history validating under AG-12's invariant, concretely, means: the reconstructed `[]ai.Message` (protected tail plus summary entry) must pass through the same pairing logic `NewSeededHistory` already runs** — whether that happens by literally calling `NewSeededHistory` on a scratch value to pre-validate, or by a new `History.compit`-style op that reuses `commitAppendOp`'s per-message rules, is an open design question (§3).
- **Pinned production invariant, verified in `harness_test.go:990-1016`**: `h.History` (the `*History` field on `Harness`) **must never be replaced by pointer** across a `Run` call — `"h.History pointer changed — Run must use the caller's history in place, never replace it"`. A "copy-then-swap-the-pointer" implementation of compaction at the `Harness` level would break this pinned test. Any compaction mutation must happen **through the existing pointee**, not by assigning a new `*History` to `h.History`.
- **`EntryID` usage is fully contained to `history.go`/`history_test.go`** (grepped repo-wide) — no other file retains an `EntryID` across a call boundary, so a compaction-induced renumbering of ordinals cannot silently invalidate a stored identity elsewhere. Compaction events correctly use `TurnID` (not `EntryID`) for their span identity, which is the safer axis (see §4 for why `EntryID` stability is explicitly NOT guaranteed across compaction).

### Cancellation tree and child-scope derivation

`harness.go:434`: `runCtx, cancel := context.WithCancelCause(ctx)` — one cancel-cause context derived once per `Run` call, threaded into every downstream call (`Turn`, and through it `Schedule`/`tool.Run`) via existing `ctx` parameters, "zero signature changes" (comment `:400-410`). There is **no per-operation child-scope derivation mechanism** beyond this single `runCtx` — `Interrupt`/`Shutdown` (`cancellation.go`) set the cause via `h.cancelRun`, and every downstream call observes it because it's the same `context.Context` value threaded through. A compaction call "cancelling independently without killing the session" (AG-18.1) most plausibly means: the compaction call is passed `runCtx` (so a run-level Interrupt/Shutdown *does* abort it), but compaction's *own* failure/timeout does **not** call `cancel()` on `runCtx` and does not route through `windDownRun` — it only produces a `compaction_failed` event and lets the run continue. No new cancellation primitive exists yet for a narrower "abort compaction only" scope; nothing in the charter requires one either (re-read the charter: "cancels via the run's cancellation tree" — i.e., participates in the existing tree, not a new branch of it).
- `windDownRun` (`harness.go:329-350`) enumerated order (R-CAN-002, verified against `agent-cancellation-tree/spec.md:61-71`): synthesize orphans → close turn → emit `cost_session(Final)` → emit `run_end` → return cause. This order is **closed and stream-validated** (`CheckStream` must accept it unmodified, `stream_check.go` byte-unchanged per the spec). AG-18.4's "compaction interrupted mid-call leaves the pre-compaction transcript intact, and the next turn proceeds" does **not** describe a run-ending interrupt — it describes an ordinary compaction-call failure (any cause, cancellation included) that must be caught locally and converted into `compaction_failed`, without ever calling `windDownRun`. See §3 for the atomicity design this implies.

### Cost/usage fold — how a per-turn figure enters the run cumulative

`cost_usage.go`: `costAccumulator.add(c CostTurn)` (`:118-130`) folds any observed `CostTurn` payload into the run-local total by simple per-figure OR-presence/sum. `harness.go:562-580`: the attempt loop's per-`Turn` forwarder goroutine reads every event off `turnSink` and does `if ct, ok := ev.CostTurn(); ok { total.add(ct) }` **before** forwarding it to `sink`, unconditionally — no `TurnID` or label filtering. Comment (`:568-574`): *"Every attempt that reaches a Completion emits its own cost_turn inside its own bracket, so this counts retries by construction, with no retry-awareness here at all."* **This means any `cost_turn` event that reaches the harness's forwarding path is automatically folded into the run cumulative with zero new code** — a strong argument for reusing the existing `cost_turn` mechanism for compaction spend, *if* compaction's model call is routed through a code path that also emits `cost_turn` on that same forwarding path (see §3, design question 5).
- `CostLabel` (`cost_events.go:90-114`) is a **closed, two-member vocabulary**: `CostLabelEstimate` (only legal on `cost_session`) and `CostLabelFinal` ("the label for every `cost_turn` figure" — verbatim doc comment `:104-106`). There is no third label. Reusing `CostTurn` as-is for compaction spend means it carries `CostLabelFinal`, indistinguishable from an ordinary turn's cost **by label alone** — distinguishability would have to come from `TurnID` correlation against the compaction bracket's own `turn` field (see §3).

### How `ai.Provider`/options are injected today

The only existing precedent for an **injected, decision-only** seam with its own typed prompt/verdict is `FailoverPolicy` (`failover_policy.go`, full file read) — structurally identical to `ContextStrategy` (one-method interface, exported-field prompt, unconstructible-by-default fieldless verdict struct, nil-default field on `Harness`, one shipped `NoOp*` implementation). **But `FailoverPolicy` never itself executes a model call** — `Resolve` only returns a verdict; execution (if any, post-v1) is deferred. AG-18.1's compaction call is a **different shape**: Layer 2 must actually *invoke* an injected `ai.ModelProvider` with injected `TurnOptions`-like options and an injected instruction string, and route its usage into `cost_turn` and its result into a history mutation. No existing code executes a *second, independent* provider call within one `Harness.Run` — this is new machinery, not a call-site reuse of `Turn()` verbatim (Turn assumes tool scheduling, permission policy, and a `TurnContinuation`; a summarization call has no tools and no user in the loop). `Turn`'s signature (`loop.go:248-255`) is `Turn(ctx, provider ai.ModelProvider, system string, transcript []ai.Message, opts TurnOptions, sink chan<- *Event)` — `provider` is already a parameter, not a `Harness` field, so `Turn` **could** in principle be reused with `h.Provider` swapped for an injected compaction provider and a `nil` or minimal `Continuation`, but that would need to suppress tool scheduling/permission entirely (open design question, §3).

## 3. Open design questions with options and tradeoffs

**Q1 — How is the compactable span's boundary computed and widened to never split a call/result pair?**
- **Option A (recommended): pure two-directional widening helper over `Entries()`.** Given a target range, scan forward for any `ToolCall` whose matching `ToolResult` lies at or beyond the current end (expand end), and scan backward for any `ToolResult` whose matching `ToolCall` lies before the current start (expand start), iterating to a fixed point (a widened boundary can itself expose a further call/result pair in the rare deeply-nested case). Pros: read-only, testable in isolation, reuses the exact ID-correlation logic `resolveOpenSet` already established as correct. Cons: new code, must be proven against adversarial interleavings.
- **Option B: History exposes the pairing index (`openCall`) as a new read-only accessor.** Pros: avoids re-deriving pairing logic. Cons: touches `history.go`'s exported surface, which `history_surface_guard_test.go` (S-HIS-030/042) closes over set-equality — any new exported route must be added to that enumeration deliberately, and `R-HIS-009`'s `L2C-07` row text ("every route ... funnels through one validating commit primitive") would need re-wording regardless. Higher blast radius for equivalent benefit.
- Recommendation: A, because it requires zero change to `history.go`'s already-guarded exported surface and keeps the widening logic auditable in one new file.

**Q2 — How is the summary entry typed so it is distinguishable from a model message while remaining a valid AG-12 history entry?**
- **Option A: extend `EntryOrigin`** with a third member, e.g. `EntryOriginSummarized`, mirroring the existing `appended`/`synthesized` split (`history.go:81-92`). Pros: reuses the exact discriminator shape already proven correct for `synthesized` (R-HIS-007's own precedent: distinguishability by envelope origin alone, never by content or `Failed()`). Cons: `EntryOrigin` is currently minted only by `History.Append`/`NewSeededHistory` (Appended) and `SynthesizeOrphans` (Synthesized) — a new commit path is needed to mint the third value, which is exactly the `R-HIS-001`/`R-HIS-004` tension in §4.
- **Option B: encode the summary as an ordinary `ai.Message` with a content-level sentinel.** Explicitly rejected by precedent: `R-HIS-007`'s own reconciliation text states a content sentinel is forgeable by a real tool and prohibited for exactly this distinguishability problem. Should not be reopened for compaction.
- Recommendation: A.

**Q3 — Does compaction run before or after the strategy consultation returns, and how is atomicity achieved (copy-then-swap vs. journal)?**
- The evidence in §1 rules out a pointer-swap at the `Harness.History` level (pinned test). The evidence in §1/AG-18.4 mapping shows the natural-by-construction answer needs no journal: **build the complete replacement message set in memory (widened span computation + the compaction call's returned summary), and only then perform a single new `History` commit operation that atomically replaces the span.** Nothing is committed until the model call has already succeeded, so an interruption never reaches the commit step — "atomic-or-absent" falls out of ordering, not out of a rollback mechanism. This also resolves the placement-in-the-loop question: compaction should run **after** `ContextStrategy.Resolve` returns a verdict requesting it, and before the next `Turn()` invocation — i.e., still inside the "gap" identified in §1, but now doing real work in that gap rather than nothing.
- A secondary sub-question this raises and leaves open: does compaction need its **own dedicated `turn_start`/`turn_end` bracket** on the stream so its `PlacementTurn` events and its `cost_turn` are stream-legal (§1's placement-timing finding)? Recommended: **yes** — treat one compaction operation as a lightweight turn bracket with its own fresh `TurnID`, inside which `compaction_started` → (compaction's own `cost_turn`) → `compaction_finished`/`compaction_failed` are nested, then `turn_end`. This requires zero changes to `stream_check.go`, `event.go`, or the `CostLabel`/`EventKind` vocabularies — it is entirely a new *call site*, not new machinery. This is the single most load-bearing design recommendation in this document and should be validated explicitly in `sdd-design`.

**Q4 — How does the on-demand entry point refuse a mid-turn demand, typed?**
- No existing "is a turn currently in flight" flag exists on `Harness` today (`Interrupt`/`Shutdown` detect "is a run in flight" via `h.cancelRun != nil` under `h.signalMu`, not "is a turn in flight" — those are different granularities). A new state flag (e.g., `h.turnInFlight bool`, guarded by the same `signalMu`) is the minimal addition; alternatively, route the on-demand request through the existing `steeringQueue`-like mechanism so it is inherently only actionable between turns. Needs `sdd-design` to pick one; both are small.

**Q5 — Does compaction spend reuse the existing `cost_turn` event, or need its own path?**
- **Corrected framing of the task's premise**: `R-CST-007` ("the scope fence: token-only, no new kind, no money, no parent aggregation," `agent-cost-events/spec.md:156-166`) is explicitly scoped to *"this capability"* (AG-16's own change) — it pins what **AG-16 itself** was not allowed to do (register a new `EventKind`, add a money field), not a standing prohibition binding all future milestones. It does not, by its own text, forbid AG-18 from adding a new `CostLabel` member if warranted. That said, given Q3's recommendation (compaction gets its own turn bracket), **the existing `cost_turn`/`CostLabelFinal` shape is sufficient as-is** — no new label or kind is needed, because distinguishability comes for free from the compaction bracket's dedicated `TurnID`, correlatable via `CompactionFinished.Span()`/the bracket's own envelope `Turn()`. Recommend: reuse `cost_turn` unmodified, own `TurnID`, no vocabulary change.

**Q6 — How are the compaction call's provider/options/instruction injected without Layer 2 authoring content?**
- `ContextVerdict` is the natural carrier (its doc comment at `context_strategy.go:47-52` already forecasts this: "AG-18 adds compaction fields non-breakingly"). Recommended shape: extend `ContextVerdict` with exported fields analogous to `ContextPrompt`'s posture — e.g. a `Compact bool` (or a non-zero-value discriminator), an injected `ai.ModelProvider`, injected `TurnOptions`-shaped options, an injected instruction string, and enough boundary information (e.g. "protect the last K turns" or an explicit `TurnID` cutoff) for AG-18.2's widening helper to compute the naive cut point before widening. This keeps "Layer 2 owns no prompt content" intact — Layer 3's strategy implementation authors the instruction string and hands it through the verdict; Layer 2 never constructs instruction text itself. Alternative (not recommended): a second seam/method beside `Resolve`. Rejected because it would consult the strategy twice per turn boundary, contradicting AG-17's "exactly once per logical turn" pin (R-CTX-001) unless carefully scoped — simpler to extend the one return value.
