## U1 — Is `prompt_tokens` inclusive of `prompt_tokens_details.cached_tokens`? (SILENT in chat scope)

**Both descriptions in full (`CompletionUsage`, schema at 31871):**

> `openapi.yaml:31879-31882` and `31927-31930`
> ```yaml
>         prompt_tokens:
>           type: integer
>           default: 0
>           description: Number of tokens in the prompt.
>         ...
>             cached_tokens:
>               type: integer
>               default: 0
>               description: Cached tokens present in the prompt.
> ```

**Finding: the chat schema is SILENT on inclusivity.** Neither description states whether `cached_tokens` is counted inside `prompt_tokens` or beside it. Searches for arithmetic/inclusivity prose in chat scope: `cache hit` → 4 hits, all the `prompt_cache_key` request parameter (44171, 44195, 79772, 79796); `included in` → 9, none usage-related; `inclusive` → 28, all time-range parameters; `subset` → 7, of which exactly one is usage arithmetic — and it belongs to the **Realtime** surface, not chat:

> `openapi.yaml:51045-51049` (`RealtimeResponse.usage.input_token_details`, schema at 50903)
> ```yaml
>               description: Details about the input tokens used in the Response. Cached tokens
>                 are tokens from previous turns in the conversation that are
>                 included as context for the current response. Cached tokens here
>                 are counted as a subset of input tokens, meaning input tokens
>                 will include cached and uncached tokens.
> ```

**Reading:** the spec spells out cached-inside-input arithmetic for Realtime ("Cached tokens **here** are counted as a subset of input tokens") but says nothing equivalent for `CompletionUsage` — the wording "here" even marks it as surface-local — so for Chat Completions the inclusivity of `cached_tokens` in `prompt_tokens` is undocumented at this commit and must be fixture-pinned, with the Realtime prose usable only as an analogy, not a citation.

>               type: integer
>               default: 0
>               description: The unadjusted number of prompt tokens written to cache.

**Finding: SILENT.** The single-sentence description ("unadjusted number ... written to cache") makes no statement of inclusion in or exclusion from `prompt_tokens`. `unadjusted` → 1 hit total (this line); `written to cache` → 1 hit (this line); no other prose anywhere references this field. The word "unadjusted" hints at billing-multiplier semantics but the spec never defines it.

**Reading:** whether cache-write tokens are a subset of `prompt_tokens` or an additional count is entirely undocumented at this commit — a fixture-pinned dialect question; the adapter must not assume `prompt_tokens >= cache_write_tokens` from the spec alone.

## U3 — Is `completion_tokens` inclusive of `completion_tokens_details.reasoning_tokens`? (YES — via explicit prose)

**Both descriptions:**

> `openapi.yaml:31875-31878` and `31901-31904`
> ```yaml
>         completion_tokens:
>           type: integer
>           default: 0
>           description: Number of tokens in the generated completion.
>         ...
>             reasoning_tokens:
>               type: integer
>               default: 0
>               description: Tokens generated by the model for reasoning.
> ```

**The inclusivity statement — in the sibling `rejected_prediction_tokens` description:**

> `openapi.yaml:31905-31918` (reflowed from YAML folded scalar)
> ```yaml
>             rejected_prediction_tokens:
>               type: integer
>               default: 0
>               description: >
>                 When using Predicted Outputs, the number of tokens in the
>                 prediction that did not appear in the completion. However, like
>                 reasoning tokens, these tokens are still counted in the total
>                 completion tokens for purposes of billing, output, and context
>                 window limits.
> ```

**Reading:** yes — the chat schema itself states that reasoning tokens are "counted in the total completion tokens" (the clause "like reasoning tokens, these tokens are still counted in the total completion tokens", 31911-31916, asserts it for both reasoning and rejected-prediction tokens), so `completion_tokens` is inclusive of `reasoning_tokens` (and of `rejected_prediction_tokens`) at this commit; this is the only usage-arithmetic sentence in chat scope (`still counted` → 1 hit total, line 31913).

## U4 — Does any chunk/choice/delta field carry the matched stop-sequence value? (NEGATIVE)

**Finding: NEGATIVE.** No response-side field echoes which stop sequence fired. Searches: `stop_sequence` → 0 hits; `stop_reason` → 0 hits; `matched` → 1 hit (44972, an eval grader's "content that should be matched" — unrelated). The streaming chunk schema (33295-33440), choice item (33313-33366), and delta (31479-31521) declare no stop-related field beyond `finish_reason` itself. The request-side `stop` parameter (`$ref` at 32963 in `CreateChatCompletionRequest`) resolves to `StopConfiguration`, whose description addresses echo semantics only negatively:

> `openapi.yaml:61713-61718`
> ```yaml
>     StopConfiguration:
>       description: |
>         Not supported with latest reasoning models `o3` and `o4-mini`.
>
>         Up to 4 sequences where the API will stop generating further tokens. The
>         returned text will not contain the stop sequence.
> ```

**Reading:** the spec guarantees the stop sequence is *stripped from* the returned text and provides no field reporting *which* sequence matched — a consumer can know only `finish_reason: "stop"`; any matched-sequence surfacing in the adapter's taxonomy must be marked non-derivable from the OpenAI-compatible wire.

The non-streaming description carries one extra sentence absent from the streaming twin:

>                   Spec](https://model-spec.openai.com/2025-12-18.html) for more.

>                   - stop
>                   - length
>                   - tool_calls

Searches: `refusal` → 92 hits, none within 20 lines of any chat `finish_reason` block (in chat scope `refusal` appears only as the delta/message content field cited in AI-28 C7 and in logprobs, lines 31517, 33341 et al.); `pause`/`paused` → 19 hits, all the fine-tuning job pause endpoint (8048-8108); `incomplete` → all hits are the Responses API `status: incomplete` / `incomplete_details` (17192 ff.), never a chat finish value.

**Reading:** chat scope defines no refusal- or pause-flavored finish semantics — a refusal streams as ordinary `delta.refusal` content and terminates with a plain `finish_reason` from the five-value enum, so the adapter's taxonomy cannot key refusal/pause off `finish_reason` for OpenAI-compatible dialects.

## U6 — Exactly one populated usage chunk per stream under `include_usage` (restated for self-containment)

**`ChatCompletionStreamOptions.include_usage` — the multiplicity language:**

> `openapi.yaml:31433-31449` (reflowed from YAML folded scalar; `[DONE]` split across 31436-31437)
> ```yaml
>             include_usage:
>               type: boolean
>               description: >
>                 If set, an additional chunk will be streamed before the `data:
>                 [DONE]` message. The `usage` field on this chunk shows the token
>                 usage statistics for the entire request, and the `choices` field
>                 will always be an empty array.
>                 All other chunks will also include a `usage` field, but with a
>                 null value. **NOTE:** If the stream is interrupted, you may not
>                 receive the final usage chunk which contains the total token
>                 usage for the request.
> ```

**Chunk-side `usage` field:**

> `openapi.yaml:33393-33405` (reflowed)
> ```yaml
>         usage:
>           $ref: "#/components/schemas/CompletionUsage"
>           nullable: true
>           description: >
>             An optional field that will only be present when you set
>             `stream_options: {"include_usage": true}` in your request. When
>             present, it contains a null value **except for the last chunk**
>             which contains the token usage statistics for the entire request.
> ```

Interruption prose on the chunk side (33408-33413): "**NOTE:** If the stream is interrupted or cancelled, you may not receive the final usage chunk which contains the total token usage for the request." The `choices` description (33306-33312) adds: choices "Can also be empty for the last chunk if you set `stream_options: {"include_usage": true}`."

**Multiplicity evidence:** the spec consistently uses the singular — "**an additional chunk**" (`additional chunk` → 1 hit, 31436), "**the last chunk**" (33402), "**the final usage chunk**" (`final usage chunk` → 2 hits, 31454 and 33410) — and defines populated usage as occurring on exactly that one chunk, with "All other chunks ... null" (31444-31446). No prose anywhere contemplates more than one populated usage chunk.

**Reading:** at most one populated usage chunk occurs per stream — the single additional chunk before `data: [DONE]`, with empty `choices` and non-null `usage`, all preceding chunks carrying `usage: null` — and it may be absent entirely if the stream is interrupted or cancelled; zero-or-one is the complete multiplicity contract.
