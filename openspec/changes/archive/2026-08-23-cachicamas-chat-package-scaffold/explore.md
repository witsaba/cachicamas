# Explore — `cachicamas-chat-package-scaffold` (CH-01)

## Current State

**Package layout today.** `backend/agent/` is one Go module (`github.com/cachicamas/backend/agent`, go.mod:1 `go 1.26.6` — note ADR 0005 § D2 states `go 1.26.3`; the go.mod has since moved past that pin, a pre-existing, CH-01-unrelated drift). Top-level `src/` packages: `agent` (Layer 2), `agenttest`, `ai` (Layer 1), `apptest`, `handoff`, `layer3handoff`. **There is no `src/cmd/` directory of any kind and no `src/chat/` or `src/coding/`** — confirmed by decision.md § 5 (`openspec/changes/archive/2026-08-23-cachicamas-chat-vocabulary-and-scope/decision.md:122-124`) and by the historical R-AGP-001 requirement that both MUST NOT exist at AG-03 time. `src/cmd/chat` will be this module's **first** composition root.

**The import guard (`backend/agent/src/agent/import_boundary_test.go`, package `agent_test`).** Five checks, each independently scoped:
1. `TestLayer2_ProductionClosure_ImportsOnlyLayer1AndStdlib_DenyByDefault` (:277) — `go list -deps` over `layer2Pattern` (`src/agent/...`), deny-by-default against `allowedProductionPrefixes`.
2. `TestLayer2_TestClosure_AdmitsOnlyTheTestSubstrateBeyondProduction` (:322) — same but `-test`, over `{layer2Pattern} ∪ layer2TestOnlyTreePatterns` (`src/apptest/...`, `src/layer3handoff/...`), one `listNonStdlibDeps` call **per pattern** (not a merged union — AG-23's own per-pattern vacuity-floor fix, S-AGP-070).
3. `TestLayer2_ProductionClosure_ContainsNoNetworkOrFilesystemPackage` (:463) — exact-path scan including stdlib, denies `net`, `net/http`, `os`, `io/fs`, with a closed, evidence-cited `forcedStandardLibraryImporters` allowlist (AG-22 correction).
4. `TestLayer2_ProductionSources_NoDirectForbiddenFamilyImport` (:581) — AST, zero-hop, per-file source scan of `src/agent`'s own non-test `.go` files against `layer2ForbiddenImportFamilies = {"os","net","syscall","io/fs"}`. **Names the file** (`filepath.Base(path)`).
5. `TestLayer2_SiblingTrees_NoDirectForbiddenFamilyImport` (:727) — same AST mechanism as check 4, applied to `src/apptest` and `src/layer3handoff` (test files included), family list = check 4's plus `"time"`. **Names the file.**

`forbiddenPrefixes` (:197) currently denies, checked first (before the allowlist): `database_administrator`, `workspace_syncer`, `src/coding`, `src/cmd`, `src/ai/openaicompat`, `otel/sdk`, `otel/exporters`, `otelslog/bridges`. Each row carries a `rule` string cited in the failure. **`src/chat` and `src/cmd/chat` do not appear anywhere in this file yet** — no scan pattern touches them, no allowlist admits them, no forbidden row exists for chat-specific concerns.

**Message-shape split, confirmed by reading the code (this bears directly on the milestone's bite proof):**
- Checks 1–3 (closure-based, `go list -deps`) name the **denied import path** and the **rule text**, e.g. (:296-303) `"...this path is neither the Go standard library nor a package this guard's production allowlist admits... adding a dependency needs its own recorded design decision..."` — this is deny-by-default framing, explicitly warning against "just add an allowlist entry." **It does not name the originating file** — `go list -deps` reports package-level closure membership, not per-file provenance.
- Checks 4–5 (AST, source-level) name the **file** (`filepath.Base(path)`) and the **family rule**, e.g. (:598-601) `"%s directly imports %q, which is in the forbidden %q family\n  rule: ADR 0005 § D1 row 2..."` — this is a named-family denial, not deny-by-default phrasing, and it is not filtered through an allowlist at all.

No existing check produces a message that simultaneously (a) names the scratch file, (b) names the denied path, and (c) uses deny-by-default framing rather than "missing allowlist entry" framing. See Open Questions.

**Byte-freeze status.** `import_boundary_test.go` is **not** byte-frozen by any pin/fence test. `scope_fence_test.go`'s `del024ByteUnchangedFiles()` (:20-32) lists only `event_descriptor.go`, `delegation_events.go`, `cost_events.go`; `import_boundary_test.go` is absent. The file's own package comment documents three prior extensions in place (AG-03 → AG-22 → AG-23), confirming it is the repo's convention to actively extend this file, never clone it — directly matching `agent-layer3-handoff` R-L3H-002's definition: *"The guard mechanism — Layer 2's single, pre-existing, deny-by-default import-boundary guard, extended (never cloned)."* (spec.md:36)

**3. `agent-package-scaffold` R-AGP-003 / R-AGP-006, quoted.**

## Approaches — how CH-01.2's guard extension could be structured

| Approach | Description | Pros | Cons | Effort |
|---|---|---|---|---|
| **A. Extend by pattern-set, mirroring AG-23's own table exactly** | Add `src/chat/...` to check 1 (production, unwidened) and to check 2's pattern set (test closure); add a new check 6 (AST source scan, files+family) over `src/chat` alone for zero-hop family denial; leave `src/cmd/chat` scanned only by a **separate**, new closure check scoped to the root's own tree (rows 1–3 admissible, root-only rows like OTel SDK admitted there and only there) | Directly reuses the AG-23 precedent this repo already has twice (Layer 1→2 at AG-03/AG-06 era, Layer 2→3-sibling at AG-23); auditable diff shape; `forbiddenPrefixes` additions (`database_administrator`, `workspace_syncer` already present — reusable rows) | AG-23's own two-mechanism split (closure-based deny-by-default vs. source-scan file-naming) does not, by itself, produce a message satisfying CH-01.2 scenario 1's **combined** file+path+deny-by-default requirement — an unresolved gap either way | Medium |
| **B. Single new combined check for `src/chat`+`src/cmd/chat` that both lists the closure AND names the originating file** | Write one check that walks `src/chat`'s own production files (AST, like check 4) but additionally resolves each denied import against the deny-by-default framing text, producing one message with all three properties | Satisfies CH-01.2's Gherkin literally, in one place, without touching existing checks 1–5 | Novel mechanism not modeled anywhere else in this file or in the AG-23 precedent; increases guard surface area und weakens the "extended, never cloned" precedent's own internal consistency (five checks become six with a structurally different shape) unless the design phase deliberately reconciles it against R-AGP-003's own extension table pattern | Medium-High |
| **C. Accept the AG-23 message-shape split for CH-01.2 too, and treat the milestone's Gherkin wording as satisfied by whichever check catches which violation class** | For "a Go package of another backend module" (forbiddenPrefixes match) — closure check already names path + deny-by-default-adjacent framing; interpret "naming the scratch file" loosely via the check-4/5 AST scan running in parallel for the same violation | Zero new mechanism; smallest diff | Requires either two checks to both fire on the SAME planted violation (so the recorded red evidence shows both a file-naming failure and a path+rule-naming failure from two different tests) or a re-reading of the Gherkin that a reviewer might reject; risks a bite-proof audit finding the scenario "not literally satisfied by one failing test" | Low, but carries acceptance risk |

## Recommendation

Approach A (extend by pattern-set) is the closest fit to this repo's own established convention and to R-AGP-003's AG-23 extension table, and should be the design's starting point. However, **the file+path+deny-by-default combined-message requirement in CH-01.2's own Gherkin is a genuine, unresolved design question that this exploration cannot decide** — it must be surfaced to a human (or explicitly settled in `sdd-design`) before implementation: either (a) the design accepts that two separate checks jointly satisfy the scenario's two "Then" clauses (closer to Approach A/C), or (b) a message-shape change is made to produce one combined failure (closer to Approach B), or (c) the milestone's own Gherkin is read as satisfied by NFR-AGP-002's existing floor and the milestone doc's stricter wording is treated as illustrative rather than literal. None of these is free of risk, and choosing wrongly either fails `sdd-verify`'s bite-proof re-read or destabilizes NFR-AGP-002's existing five-check contract.

## Risks

- **R-AGP-001 is directly falsified by CH-01.1's own deliverable.** `agent-package-scaffold/spec.md` R-AGP-001 states `…/src/cmd/` "MUST NOT exist in any form, including as an empty directory." CH-01.1 creates `src/cmd/chat/`. This is not a hypothetical future conflict — the promoted spec is wrong the day CH-01.1 merges, unless a spec delta lands in the same change. This must be scoped into `sdd-propose`/`sdd-design`, not discovered at `sdd-verify`.
- **Two independently-plausible failure-message designs (Approach A vs. B) produce materially different diffs and different risk to NFR-AGP-002's existing contract** — picking without a recorded decision risks re-litigating the guard's shape mid-implementation.
- **ADR 0005 has no row for `src/chat`/`cmd/chat`.** If the design silently assumes "chat inherits `src/coding`'s row 3 and `cmd/cachicamas`'s row 4 by analogy," that assumption is currently undocumented anywhere machine-checkable; a future reviewer could reasonably ask where that inheritance is stated.
- **"Layer 2 internals" (milestone Notes, 0005:241) is ambiguous** between "the whole `src/agent` package" (which would contradict ADR 0005 row 3's explicit permission for Layer 3 to import Layer 2) and "Layer 2's test-only substrate" (`src/agenttest`, and by extension `src/apptest`/`src/layer3handoff`) — these need explicit resolution before the forbidden-prefix rows for CH-01.2 can be written.
- **The Makefile's own comment (`Makefile:96-98`) names `cmd/cachicamas` (doc 0004) as "the" composition root arriving next**, but doc 0005's chat root is arriving first. This is cosmetic (no functional Makefile change needed) but should be noted so a reviewer doesn't read the stale comment as a planning contradiction.

## Open Questions — do not assume, coordinate instead

These are things this exploration deliberately did NOT decide, per the "do not assume, coordinate instead" instruction. Each lists candidate answers and the evidence bearing on it.

1. **What is `src/chat`'s Go package identifier?** Only the directory path `backend/agent/src/chat/` is stated anywhere (decision.md:122, R-CHT-007). Candidates: (a) `package chat` (Go convention: package name matches last path element, mirrors `src/agent` → `package agent`); (b) something else entirely uncited. No artifact states this explicitly. **Recommend (a) by convention, but this must be a stated decision, not an inference this exploration makes binding.**

2. **Does `src/chat` ship as a doc.go-only package for CH-01.1, mirroring R-AGP-001's original AG-03 shape** (`package agent` + doc comment + nothing else, before AG-04 added behavior)? The milestone's own Notes say "the packages ship empty of policy" (0005:241) and CH-01.1's out-of-scope clause is "any behavior." This strongly suggests yes, but no artifact states "ship a `doc.go`" as a concrete file-shape decision, and R-AGP-001 itself (the literal precedent) is a promoted requirement for **Layer 2**, not stated as binding on Layer 3's own scaffold milestones.

3. **Is `src/cmd/chat/main.go` a literal empty/near-empty stub (e.g. `func main() {}` or a one-line placeholder), or does it need to at least compile a non-trivial `package main` with a doc comment stating its future role** (as `src/agent/doc.go` did at AG-03)? CH-01.1's charter says "ships empty of policy" but doesn't state the file's literal shape.

4. **How does the extended guard name the archetype's position in its failure messages?** — i.e., does a denied import inside `src/chat` get a `forbiddenPrefixes`-style row citing "ADR 0005 § D1 [row N]: [text]" the way existing rows do, and if so, which row number, given ADR 0005's table has no literal row for `src/chat`? Does the guard extension cite the milestone doc's own Notes (0005:241) instead, or does this require an ADR 0005 amendment first?

5. **Does the archetype package (`src/chat`) import Layer 1 (`src/ai`) directly, or only through Layer 2 (`src/agent`)?** ADR 0005 § D1 row 3 (Layer 3 `coding`) explicitly permits importing "rows 1–2" (both Layer 1 and Layer 2). No chat-specific artifact confirms whether the SAME permission is intended for `src/chat`, or whether the archetype is meant to consume Layer 1 exclusively through Layer 2's own re-exported surface. This directly determines what `allowedProductionPrefixes`-equivalent entries CH-01.2 must admit for the archetype's own scan.

6. **What exactly does "Layer 2 internals" (0005:241, the fourth forbidden-closure item) forbid?** Candidates: (a) the entire `src/agent` package — contradicted by ADR 0005 row 3's explicit permission, so likely wrong; (b) `src/agenttest` (Layer 2's test-only substrate) — consistent with R-L3H-001's "MUST NOT rely on a helper declared in a Layer 2 test file" and with CH-02's charter statement that "the projection is the archetype's only reading of Layer 2 (R-05)"; (c) `src/agenttest` **plus** `src/apptest` and `src/layer3handoff` (AG-23's own kit/proof trees) — plausible since those are equally "internal" to Layer 2's own consumer-proof machinery, not meant for a real archetype. No artifact states which.

7. **How is the file+path+deny-by-default combined-message requirement (CH-01.2 scenario 1's two "Then" clauses) satisfied mechanically?** Detailed under Approaches/Recommendation above — this is the single largest unresolved design question, because no existing check in `import_boundary_test.go` currently produces a message with all three properties at once, and AG-23's own precedent (the closest prior art) split the same obligation across two different check types rather than combining them.

8. **Does ADR 0005 itself need a delta/amendment adding `src/chat` and `cmd/chat` rows to its § D1 and § D3 tables**, or is the milestone doc's own Notes section (0005:241) treated as sufficient normative authority for CH-01's guard extension without touching the ADR? Given this repo's precedent of ADRs fixing decisions rather than being extended per-archetype casually (see the `adr-fixes-decisions-not-filenames` convention already established for ADR 0009), this is a real fork with a real cost either way and should be a human decision, not an inferred default.

9. **Does R-AGP-001's contradiction (open question / risk above) get resolved by a spec delta inside `cachicamas-chat-package-scaffold` itself, or does it require its own separate SDD change against `agent-package-scaffold`?** The `chat-archetype-contract` precedent (CH-00) shows this repo's convention of recording defects without repairing them (F-1/F-2/F-3, disposition "recorded, not repaired" — decision.md § 10) — but R-AGP-001 is not a mere inconsistency between two artifacts, it is a **promoted requirement that becomes literally false** the moment CH-01.1 merges. This is qualitatively different from CH-00's F-1/F-2/F-3 (both-sides-cited inconsistencies with no forcing merge) and likely needs an actual spec delta, not a recorded-not-repaired register entry. This determination should not be made silently in `sdd-propose`.

10. **Does `backend/agent/Makefile` need a per-binary build target for `cmd/chat`** (the way `database_administrator` and `workspace_syncer` each have named binary outputs in their own Makefiles), or does CH-01.1's "the composition root's binary builds" check evidence get satisfied by the existing bare `go build ./...`/`go vet ./...` targets with no Makefile edit at all? No artifact states this, and `backend/agent/Makefile`'s own comment anticipates a **different** archetype's root (`cmd/cachicamas`) arriving first, so this Makefile has never actually been exercised with a real `package main` before.
