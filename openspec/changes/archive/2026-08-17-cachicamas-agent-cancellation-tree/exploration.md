# Exploration — `cachicamas-agent-cancellation-tree` (AG-14: build the cancellation tree)

> Phase: sdd-explore · Change: cachicamas-agent-cancellation-tree · Milestone AG-14, doc 0003 lines 1371-1442
> Depends on: AG-13 (run driver, archived, merged 52701436). Parallel with: AG-15, AG-16.
> Charter: two distinguishable signals — interrupt (abort turn, keep session) and shutdown (flush and exit) — propagated loop→provider→tools, bounded wind-down, typed post-signal harness state.

## Current state — how a run/turn is driven today

`Harness.Run(ctx, prompt, sink)` (`backend/agent/src/agent/harness.go:218-330`) drives `Turn` in a loop, sharing one `runID`/`stamper`/`Scheduler`/`History` via `TurnOptions.Continuation` (`loop.go:62`, `TurnContinuation` fields at `loop.go` near :247). `ctx` flows unmodified: `Run(ctx, ...)` → `Turn(ctx, h.Provider, ...)` (`harness.go:289`) → `provider.Stream(ctx, req)` (`loop.go:331`) and → `sched.Schedule(ctx, ...)` (`loop.go:368`, called from within `Turn`'s tool-dispatch branch). Inside `Schedule` (`scheduler.go:117`), `ctx` reaches `scheduleRead`/`scheduleSerialized` → `executeCall` → `runPermissionGate` (only place that actually selects on `ctx.Done()` today, `scheduler.go:637,657`). **Critically, `executeCall` calls `tool.Run(context.Background(), runArgs, ...)` (`scheduler.go:462`) — the running tool itself never receives the run's `ctx`.** Only a *parked* (awaiting permission decision) call observes cancellation; an already-executing tool cannot.

`RunOutcome` already has three members: `Completed`, `Interrupted`, `Failed` (`run_events.go:100-118`) — `RunOutcomeInterrupted` was reserved at AG-04 and is used nowhere in production code yet, only in `stream_check_test.go:147-153` to exercise the validator's own `String()`. `TurnOutcome` has `Finished|Aborted|LengthLimited|ToolCalls|ContentFiltered|Refused|Paused|Unknown` (`turn_events.go:74-119`) — no cancellation-specific member; `TurnOutcomeAborted` is the only "something went wrong" outcome and it requires a non-nil `*Failure`. `ai.FailureCategory` already has a `Cancellation` member (`provider_failure.go`) used throughout Layer 1 and by `agenttest`'s fake provider — `FailureCategoryCancellation` is emitted when `ctx.Err() != nil` at pre-stream (`fake_provider.go:85-97`). Layer 1's cancellation-fidelity contract for the scripted fake lives in `backend/agent/src/agenttest/conformance_cancellation.go` (R-CNF-011/R-CNF-012): cancelling `ctx` mid-stream makes the fake's `produce` goroutine (`fake_provider.go:192-210`) select on `ctx.Done()` on every send and return, closing the channel **bare** (no terminal event) unless the test script explicitly emits one — the fake does NOT synthesize a cancellation error terminal itself (only real openaicompat adapters do, per R-AEM-014).

`History.SynthesizeOrphans()` (`history.go:270-300`) already exists and is exactly AG-14.1's "orphan synthesis" step: it walks `h.open`, and for each unresolved tool call appends a synthesized `ai.RoleTool` failure message with fixed content `synthesizedInterruptionContent` (`history.go:251`), then the harness can call `CloseTurn()` cleanly. Nothing in AG-13 calls `SynthesizeOrphans` — the harness's normal path always closes turns with an empty open set.

`Harness.failRun` (`harness.go:200-207`) is the ONLY typed-failure exit today: on any non-nil `Turn` error it calls `wrapHarnessFailure(cause)` (`harness.go:183-192`), which **unconditionally** builds `ai.MidStreamFailure(ai.FailureReport{Category: ai.FailureCategoryUnavailable, Cause: cause}, false)` — regardless of whether `cause` is actually a cancellation — then emits `NewRunEnd(runID, RunOutcomeFailed, failure)`. So today, cancelling `ctx` before/between turns and letting the next `Turn` call fail (`provider.Stream` returns a pre-stream `FailureCategoryCancellation` failure) surfaces on the stream as `RunOutcomeFailed` / category `Unavailable` — silently mis-categorized. `agent-run-driver/spec.md:211-217` (`R-RUN-011`) is the spec requirement that currently pins this "any error → Failed" behavior and will need an amendment.

`Turn` itself (`loop.go:247-431`) has **zero** `ctx.Err()`/`ctx.Done()` checks anywhere in its own body (verified — grep across `backend/agent/src/agent` finds `ctx.Done()`/`ctx.Err()` only in `scheduler.go` and `permission_protocol.go`, never in `loop.go`). When `provider.Stream`'s channel closes with no `Completion` and no error event (exactly what happens when the fake closes bare on cancellation), `Turn` falls into the "provider closed without a Completion" branch (`loop.go:417-427`) and **defaults the finish reason to `ai.FinishReasonStop`** — i.e. an interrupt that races a bare channel close is silently treated as a normal, successful turn completion today. This is the loop-level gap AG-14.1 must close.

## The gap

1. **No cancellation-cause detection at the loop's closed-channel branch.** `loop.go:417-427` must distinguish "provider genuinely ran out of events" from "the channel closed because `ctx` was cancelled" — currently indistinguishable.
2. **Tool execution is `context.Background()`-detached** (`scheduler.go:462`). A running tool cannot observe run cancellation at all; only a parked (not-yet-executing) call can, through the permission gate's `ctx.Done()` select. This is why AG-14.3's "cancellation-deaf tool" scenario is not a corner case — it is the *default* behavior of every tool today.
3. **`Schedule`'s `wg.Wait()` (`scheduler.go:205`) is unbounded.** If a call goroutine never returns (as in gap 2), `Schedule` never returns, so `Turn` never returns, so `Harness.Run`'s loop iteration never returns. There is no existing bound anywhere in this call chain — AG-14.3 must introduce one.
4. **No typed run-level cancellation-cause routing.** `failRun`/`wrapHarnessFailure` hardcode `FailureCategoryUnavailable` and `RunOutcomeFailed` for every `Turn` error (`harness.go:183-207`); a cancellation-caused error is mis-typed today.
5. **No distinguishable *shutdown* outcome exists anywhere.** `RunOutcomeInterrupted` is reserved and unused; there is no `RunOutcomeShutdown` (or equivalent). `RunEnd.validate` (`run_events.go:152-163`) forbids attaching a `*Failure` to any outcome except `Failed`, so today a `RunOutcomeInterrupted` run-end cannot itself carry an interrupt-vs-shutdown discriminator — that information, if it is to live on the stream, needs either a new outcome member or a new payload field, both of which are substrate edits (see below).
6. **No post-signal harness "refuses new prompts" state.** `Harness` (`harness.go`) is a fresh value per `Run` call today (design.md: "One `Run` per `Harness` value; cross-run state is AG-21"); AG-14.2's "subsequent prompts fail typed" scenario implies the harness value itself must remember it was shut down, which is new state AG-13 never needed.
7. **No bound/deadline vocabulary or wind-down timer exists in this package.** Zero `time.After`/deadline usage in `backend/agent/src/agent` production code (confirmed by the scheduler/loop reads above) — AG-14.3's "documented bound" is a wholly new mechanism.

## Design tensions to resolve (for `sdd-design`)

### 1. How interrupt and shutdown stay distinguishable through every layer

Two realistic Go options:

| Option | Mechanism | Tradeoff |
|---|---|---|
| **A — typed cause alongside `ctx`** | A `context.Value` key or a parallel field (e.g. `TurnContinuation.CancelCause` / a `context.Cause(ctx)` using Go's `context.WithCancelCause`) carrying an enum `{Interrupt, Shutdown}`, read at every point that currently reads `ctx.Err()` | `context.WithCancelCause` (Go 1.20+) is stdlib, no new dependency (satisfies R-01's import guard); `context.Cause(ctx)` is inspectable at any depth without threading an extra parameter through `Turn`/`Schedule`/`executeCall`'s already-long signatures. Cleanest fit for "propagated down through loop, provider and tools" since it rides the existing `ctx` parameter these functions already take. |
| **B — separate channel/state on `Harness`** | `Harness` exposes `Interrupt()`/`Shutdown()` methods that internally call a stored `context.CancelCauseFunc`, or a `chan cancelSignal` the run-loop selects on between turns | Requires a stateful `*Harness` (constructor or exported mutable fields) — tension with AG-13's "value-form struct, no constructor" precedent (`design.md:173`, "Scheduler precedent; no second implementation exists"). Two coordination primitives (ctx + a second channel) is more surface for less benefit than A. |
| **C — distinct `context.Context` types/keys per signal, no shared cancel** | Interrupt cancels a turn-scoped derived context; shutdown cancels the harness's own root context; loop/scheduler check both | Two contexts to thread everywhere `Turn`/`Schedule` currently take one — larger signature churn, contradicts AG-13's "no signature change" precedent for `Turn` unless routed through `TurnContinuation` (which is nil-default only for run-continuation, not naturally a second-context carrier). |

**Recommendation for design to verify:** Option A (`context.WithCancelCause` + `context.Cause(ctx)`), because it needs zero new parameters on `Turn`, `Schedule`, `executeCall`, or `tool.Run` — every one of those already receives `ctx`. The harness owns a `context.CancelCauseFunc` for the run's own top-level context (derived once at `Run` entry from the caller's `ctx`), and `Interrupt()`/`Shutdown()` call it with a typed sentinel error (`agent.ErrInterrupted` / `agent.ErrShutdown`) that `errors.Is` can match anywhere downstream, including inside a tool if AG-14 finally threads real `ctx` into `tool.Run` (closing gap 2 above — itself a design decision, since it changes `executeCall`'s call to `tool.Run`, `scheduler.go:462`, from `context.Background()` to `ctx`, which is a **behavior change every existing `ScriptedTool`/`BlockingScriptedTool` test may currently rely on NOT observing** — must be checked against `scripted_tool_test.go` and `loop_permission_e2e_test.go`).

### 2. Typed interrupted/shutdown *outcome*, not bare `context.Canceled`

`failRun`/`wrapHarnessFailure` (`harness.go:183-207`) must stop hardcoding `FailureCategoryUnavailable` and `RunOutcomeFailed`. The natural fix: when the `Turn` error (or `context.Cause(ctx)`) matches the new sentinels, route to `RunOutcomeInterrupted` instead of `Failed`. But `RunEnd.validate` (`run_events.go:152-163`) currently forbids ANY `*Failure` on `RunOutcomeInterrupted` — so either (a) `RunOutcomeInterrupted` stays failure-less on the stream and the interrupt/shutdown distinction rides purely in the **error chain** returned by `Run` (i.e. `errors.Is(err, agent.ErrShutdown)`), not on the stream itself, or (b) `run_events.go`'s validate rule is amended to also allow (or require) a `*Failure` on `Interrupted`, or a **new `RunOutcomeShutdown` member is added**. Both (b) options touch `run_events.go`, which is a **named `R-LSK-004` substrate file** (`openspec/specs/agent-loop-skeleton/spec.md:84`) — currently forbidden without an explicit, scoped release (the AG-11 precedent for `turn_events.go`/`failure.go`, spec.md:86, is the template: "released for AG-11 only," "does not extend to any milestone after AG-11 without its own recorded delta"). **This is the load-bearing open question `sdd-design` must resolve**: does AG-14 request its own scoped substrate release for `run_events.go` (to add `RunOutcomeShutdown` and/or loosen the failure-iff-Failed rule), or does it keep the stream-level outcome coarse (`Interrupted` for both) and push the fine distinction into the Go error chain only? The charter's exact wording — "Both distinguishable in run-end outcomes and error chains" (plural, both nouns) — reads as requiring the stream-level distinction too, which argues for the substrate release. `turn_events.go`/`failure.go` may also need a similar release if `TurnOutcomeAborted` needs a cancellation-specific sibling or `Failure` needs a new accessor.

### 3. Bounding wind-down against a cancellation-deaf tool (AG-14.3)

Given gap 2/3 above (`tool.Run` gets `context.Background()`; `Schedule`'s `wg.Wait()` is unbounded), the wind-down bound cannot rely on the tool ever returning. The mechanism has to be: on interrupt/shutdown, `Schedule` (or a caller around it) races `wg.Wait()` against a deadline (`time.After` / a derived deadline context). If the deadline fires first, `Schedule` must return anyway with whatever results are already populated, and the still-running call goroutine(s) become **detached**: not joined by `wg.Wait()`, but each one must be *named* — reported through a typed value carrying which tool, which call ID, and that it is still running (a new `Result` outcome or a dedicated event/field) — rather than silently dropped. Two things must both be true simultaneously, and reconciling them is the actual design work:
- **"detached and named, not silently abandoned"** — the goroutine keeps running in the background past the bound, and something durable records that fact.
- **"no task belonging to the harness itself remains after the wind-down"** (AG-14.3's third Then) — the harness's OWN machinery (the dispatcher goroutine `runDispatcher` at `scheduler.go:267`, the per-turn forwarder goroutine in `harness.go:274-279`, `Schedule`'s own bookkeeping) must fully unwind and not leak, even while the one detached tool-call goroutine survives past the bound.

The resolution is a scope distinction: "the harness's own tasks" = `runDispatcher`, the forwarder, `Schedule`'s own control-flow goroutine — all of which the bound must let exit cleanly (e.g. `emissions`/`sink` channels get closed via the abandoned-tool-safe pattern already established for permission-gate parking, `scheduler.go:206-225`'s D-B "provably unreachable-with-effect" reasoning is the closest existing precedent for this kind of proof). The ONE excluded goroutine is the tool call itself — which was never "the harness's own" in the sense that its lifetime is owned by third-party tool code the harness cannot kill (Go has no goroutine-kill primitive). `backend/agent/src/agenttest`'s `RequireNoGoroutineLeak` (`stream_kit_leak.go:107`) is not currently used anywhere in `backend/agent/src/agent` — AG-14's own tests will be the first Layer-2 use of it, and the milestone doc's own words ("the later package-wide leak sweep depends on this report being precise," `0003:1439`) explicitly defer a *package-wide* sweep to a later milestone (likely AG-21, "the assembled whole" — `0003:2264`) — AG-14 only needs to prove its OWN new goroutines don't leak and that the one intentionally-detached tool goroutine is accounted for, not invisible.

`BlockingScriptedTool` (`backend/agent/src/agent/scripted_tool_test.go:70-83`) already exists and, unmodified, is a ready-made cancellation-deaf fixture: its `Script` discards `ctx` (`func(_ context.Context, _ []byte, _ agent.PolicySlot)`) and blocks on `<-release` — a test that never closes `release` reproduces AG-14.3's "cancellation-deaf tool" exactly with zero new test infrastructure.

### 4. Interrupt during a permission suspension (AG-14.1 scenario 2)

This is the one signal-vs-signal seam that is *already* half-built: `runPermissionGate`'s parked-wait select (`scheduler.go` around :637-666, both `scheduleRead` and `scheduleSerialized` call sites) already races `WakeParked` against `ctx.Done()` and, on `ctx.Done()`, calls `typedExecutionFailureFromError(call.ID(), ctx.Err())` (`:639`, `:665`) then `parked.remove(callID)` (per `permission_protocol.go:197-211`'s doc comment, which explicitly names "context cancellation while genuinely parked" as one of `remove`'s two call sites). Today this path aborts the call with a **generic** typed execution failure keyed off raw `ctx.Err()` (`context.Canceled`), not a typed interrupted/shutdown outcome — if Design 1 adopts `context.Cause(ctx)`, this exact call site (`ctx.Err()` → `context.Cause(ctx)`) is where the interrupt/shutdown distinction must be threaded through to the tool result and, transitively, to "history closes cleanly" (`SynthesizeOrphans` covers the History side already).

### 5. Idempotency of a second interrupt (AG-14.1 scenario 3)

If Design 1 lands on `context.WithCancelCause`, this is close to free: `cancel(cause)` on an already-cancelled context is a documented Go no-op (the first cancellation wins; subsequent calls do nothing). The remaining design obligation is purely at the `Harness` level: a second `Interrupt()`/`Shutdown()` call on an already-winding-down (or already-shut-down) `*Harness` value must not panic, must not double-close any channel, and must not race the first call's cleanup — likely a `sync.Once` or an atomic state flag guarding the cancel-cause invocation and whatever "refuses new prompts" flag AG-14.2 introduces.

### 6. Reuse of R-09's upward path vs a new entry point

`agent-run-driver/spec.md:200` states explicitly: **"richer cancellation vocabulary is AG-14's"** — R-09's upward path (permission decisions, steering, and interrupts "re-enter a live run through one decided upward path," doc 0003 R-09, traced to AG-01.1/AG-10.1/AG-13.2/**AG-14.1**, `0003:2207`) is architecturally meant to be the SAME upward arrow `Steer` already uses (`Harness.Steer`, `harness.go:149-151`) and the frontend's permission-decision resume already uses (v2 §2.2's single upward arrow, `0001:274-276`). The natural fit: `Harness` gains `Interrupt()`/`Shutdown()` methods sitting alongside `Steer()`, using the same "the harness reaches the loop through no privileged channel" posture (`R-RUN-006`) — these do not call into the loop directly, they only flip state/cancel a context the loop already observes. This keeps AG-14 from needing a new entry point distinct from AG-13's established `Steer`-style surface, and is the option that best satisfies "no privileged channel" precedent without new design.

## Explicit non-goals (from the charter, restated)

- **Subagent inheritance** — AG-19.2. v2 §4.2 says "Subagents inherit cancellation from their parent," but no subagent tool ships in v1 (`0003:1794`) and AG-19 owns it.
- **Frontend signal wiring** — Layer 3. AG-14 defines the mechanism `Harness.Interrupt()`/`Shutdown()` (or equivalent); wiring a TUI keypress or a signal handler to call it is `cachicamas_coding`'s composition root, not this milestone.
- **Retry/failover** — AG-15, parallel with AG-14. A cancellation is never retried; that boundary already exists structurally (`R-RUN-011`'s "no retry" rule).
- **Cost accounting** — AG-16, parallel. A partially-completed, interrupted turn's cost is out of scope here.
- **Compaction** — AG-17. Compaction's own cancellation-safety ("recoverable if interrupted," v2 §4.2) is a later milestone's concern; AG-14 does not need to make compaction calls cancellation-aware, only the ordinary turn/tool path.

## Recommendation

Adopt `context.WithCancelCause` (§1 Option A) as the propagation mechanism, add `Harness.Interrupt()`/`Shutdown()` alongside the existing `Steer()` upward-path surface (§6), and treat the substrate-release question (§2) as the FIRST decision `sdd-design` must close explicitly and in writing — mirroring AG-11's and AG-13's own precedent of naming exactly which `R-LSK-004` file is released, for what change, and why — before any implementation code is written, because it gates whether `run_events.go`/`turn_events.go`/`failure.go` are touched at all. The bounded-wind-down mechanism (§3) is the second load-bearing decision and should be verified against a real prototype of `Schedule`'s bounded `wg.Wait()` before `sdd-tasks` commits to a shape, because it is the one piece of this milestone with no existing partial implementation to extend (unlike interrupt-during-suspension, which already has 80% of its plumbing in `runPermissionGate`).

Must be scoped as tightly as AG-11's precedent ("confined to R-ATT-001 and R-ATT-006," `agent-loop-skeleton/spec.md:86`) or reviewers will read it as re-litigating AG-04's frozen vocabulary wholesale.
