# Design: Opt-in dependency vulnerability check for `frontend/`

## Technical Approach

Mirror `backend/database_administrator`'s opt-in `vuln-check` shape using the frontend's native tooling: `package.json` scripts wrapping the built-in `pnpm audit` (no new tool install — simpler than the backend's `./bin` auto-install, which pnpm makes unnecessary). Per the accepted proposal decisions: the **full-tree** audit is the gate (not prod-scoped), `@auth/core` is remediated in the same change, and the dev-only `vitest` critical is documented as accepted baseline debt that keeps the gate red until its own change lands. Nothing is wired into `verify`, `build`, or the Dockerfile.

## Architecture Decisions

### Decision: Script names and tiering

**Choice**: Three scripts, none named `audit` (a script named `audit` is shadowed by pnpm's builtin — `pnpm audit` would ignore it):

| Script | Command | Role |
|---|---|---|
| `vuln-check` | `pnpm audit --audit-level=high` | **The gate**: full tree incl. devDeps; non-zero exit on any high/critical |
| `vuln-check:prod` | `pnpm audit --prod --audit-level=high` | Informational: shippable-runtime view; expected exit 0 after this change |
| `vuln-check:ci` | `pnpm run vuln-check` | Alias reserved for future CI wiring (mirrors backend `vuln-check/ci`) |

**Alternatives considered**: single full-tree script (loses the "is production clean?" signal that distinguishes accepted dev debt from real shipping risk); prod-scoped gate (rejected by user decision #3).
**Rationale**: full tree is the gate per user decision; `vuln-check:prod` is kept because it is the only green signal available while the gate is red on the vitest baseline. Names mirror the backend targets exactly.

### Decision: `@auth/core` remediation requires a pnpm override, not just a bump

**Choice**: bump the direct dependency to exact `0.41.3` **and** add `overrides: { "@auth/core": "0.41.3" }` to `frontend/pnpm-workspace.yaml` (pnpm 11 settings location).
**Alternatives considered**: direct bump only — insufficient. `@auth/qwik@0.9.2` hard-pins `@auth/core@0.41.2` as a regular dependency (verified in its installed `package.json`; not a peer dep), so without the override the tree keeps a second, vulnerable `0.41.2` copy that is exactly the one the login path imports, and the audit stays red on GHSA-7rqj-j65f-68wh.
**Rationale**: the override forces a single tree-wide `0.41.3` resolution, including under `@auth/qwik`. `0.41.2 → 0.41.3` is the patch containing only the security fix; ADR-0001's `@auth/qwik@0.9.2` pin is untouched. Because it is a regular (not peer) dependency, no peer-conflict error will occur — compatibility is proven by install + e2e, per the probe below.

**Compatibility probe (run before committing to either path)**:
1. `pnpm view @auth/core@0.41.3 version` — confirm the patch exists on npm.
2. Apply bump + override; `pnpm install` — must complete without resolution errors.
3. `pnpm why @auth/core` — must show a single `0.41.3`, including under `@auth/qwik`.
4. `pnpm verify` and `pnpm test:e2e` (sign-in specs are the safety net: `e2e/github-sign-in.spec.ts`, `sign-in-landing`, `sign-in-denied`, `sign-in-cookie-attrs`, `sign-out`).

**Fallback (user decision #2)**: if any probe step fails and is not trivially resolvable, drop the bump and the override, record `@auth/core@0.41.2` / GHSA-7rqj-j65f-68wh in "Current baseline" as accepted debt, and note in README + ADR-0001 that a follow-up change must resolve the ADR-0001 conflict.

### Decision: Pin `packageManager: pnpm@11.8.0`

**Choice**: add `"packageManager": "pnpm@11.8.0"` (exact — corepack requires it) to `frontend/package.json`.
**Alternatives considered**: `engines.pnpm` range (not enforced by corepack); no pin (status quo).
**Rationale**: `11.8.0` is the version producing the current install (`node_modules/.modules.yaml`) and postdates pnpm's `/advisories/bulk` audit-endpoint fix (PR #11268, 2026-04-15), so a contributor on a pre-fix pnpm cannot silently break audit correctness. `frontend/Dockerfile:32-33` already runs `corepack enable` expecting this field.

## Data Flow

    pnpm vuln-check ──→ pnpm audit (lockfile) ──→ npm advisories/bulk endpoint
                                                        │
    exit 0 / non-zero (high+ found) ←────── findings ───┘

## README structure (mirrors backend)

`## Vulnerability scanning` — commands, note `pnpm audit` is NOT reachability-aware (unlike `govulncheck`), gate semantics, opt-in status. `### Current baseline` — tool (`pnpm@11.8.0 audit`), snapshot date 2026-08-01, finding counts **taken from actual apply-time audit output**, accepted-debt table with the vitest entry (GHSA-5xrq-8626-4rwp, dev-only, blocked on `0.34 → 3.2.6` multi-major upgrade, keeps `vuln-check` red by design). `### Remediation history` — 2026-08-01 `@auth/core` bump + override entry (or fallback baseline entry).

## Testing Strategy

| Layer | What to Test | Approach |
|-------|-------------|----------|
| Install | Single `@auth/core@0.41.3` resolution | `pnpm install`; `pnpm why @auth/core` |
| Gate | Exit codes match documented semantics | `pnpm vuln-check` (non-zero, dev-only findings remain); `pnpm vuln-check:prod` (exit 0) |
| Regression | Existing behavior untouched | `pnpm verify`; `pnpm build` |
| E2E | Login path after the bump | `pnpm test:e2e` (sign-in/sign-out specs) |

## Threat Matrix

N/A — all rows: scripts are static, fixed-flag invocations of pnpm's builtin `audit`; no dynamic argument composition, no Git/PR automation, no executable-file classification, no new subprocess boundary beyond existing `package.json` script conventions.

## Migration / Rollout

No migration. Rollback = revert the PR; scripts are additive and unreferenced by `verify`/`build`/Docker. If only the bump misbehaves post-merge: remove the override, restore `0.41.2`, `pnpm install`, move the finding to "Current baseline".

## Open Questions

None — the proposal question round resolved gate scope, remediation inclusion, and the fallback path.
