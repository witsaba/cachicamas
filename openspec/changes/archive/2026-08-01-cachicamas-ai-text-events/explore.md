## Current State

**Neither AI-14 nor AI-15 is on disk yet.** Doc 0002's own status line says "14 of 41 milestones shipped, AI-00 through AI-13 landed." `backend/agent/src/ai/` has no `event*.go` file of any kind — grepped for `event|Event` and the only hits are unrelated identifier collisions (`import_boundary_test.go`, etc.). So this exploration is against the charter and the architecture reference exclusively, not against any landed event envelope or response-lifecycle code, exactly as instructed.

What *is* landed and directly load-bearing for AI-16's design:

- **The content-part pattern (AI-06, `content_part.go` + `text_content.go`)** is the house style AI-16 will most closely mirror: a closed, append-only, uint8-backed kind vocabulary (`PartKind`), a name-table `partKindNames` indexed by the constant (never a map — "nothing may let an unordered iteration decide anything"), a `partPayload` interface with unexported `kind()`/`validate()`, one file per kind, a `New<Kind>` constructor as the only door in, and a `(p Part) <Kind>() (T, bool)` accessor. AI-06.4's exhaustiveness guard (`content_part_registry_test.go`) parses the package's own `go/ast` to compare three independent answers (declared constants, `PartKinds()`, `partKindNames`) so a kind added without one of the five steps fails a test rather than shipping silently. AI-14's own event-kind registry is near-certain to reuse this exact shape (AI-14.1 test 3 — "every registered kind has a constructible payload, asserted as a table over the registry" — is the same sentence as AI-06.4's rationale).
- **`textPayload` (`text_content.go`) already defines the normalized text shape** AI-06 shipped: a bare `string`, stored and returned byte-for-byte, with exactly two rules — non-whitespace-only (`ErrEmpty`) and `<= MaxTextLen` bytes (`ErrOutOfRange`). Critically, `NewText`'s emptiness rule (`strings.TrimSpace(t.text) == ""` fails) is a *content-part* rule about a complete, model-visible text value. It must **not** be reused verbatim for a streamed delta fragment: AI-16.3 requires a block with **zero deltas** to be legal, and nothing in the charter forbids an individual delta fragment from being whitespace-only or even zero-length. Applying `textPayload.validate` to a delta would silently break both AI-16.3 and ordinary whitespace-only tokens a real model emits (e.g. `" "` between words as a separate delta).
- **`tool_call.go`'s `ToolCalls()` doc comment states the package's existing position on ordinals**: the *content-part* ordinal (a tool call's position among calls in a finished message) is deliberately **derived**, never stored, because storing it would be "a second copy of a fact the sequence already holds" that two writers could disagree about. This is the opposite of what AI-16.1 needs: a text block's start/delta/end events are **separate, time-ordered stream events that may interleave with another block's events** (and, per AI-17/AI-18, with reasoning and tool-call block events too). There is no finished sequence to derive a position from at emission time, so the block index **must be carried explicitly on each event**, stamped by the producer — closer to AI-14.2's per-stream sequence (explicitly stamped, guarded against becoming a package-global counter by AI-14.3) than to `ToolCalls()`'s derived ordinal.
- **`validation.go`'s `Path`/`Step`/`AtIndex` machinery** is the existing positional-error idiom (`content[0].text`); if AI-16 needs to report a caller-contract failure on a malformed event, this is the mechanism, and `AtIndex("content", i)` already sets precedent for how a block index could compose into a rendered position (e.g. an eventual `AtIndex("blocks", i)`).
- **Doc 0001 § 4.3, "four invariants the envelope must satisfy"**, invariant 1 verbatim: *"Deltas carry an index, never a snapshot of the accumulated message. Emitting a full message copy per token is a data race if shared and quadratic allocation if copied. Consumers accumulate."* AI-14.4 item 2 restates this exact invariant and is the citation AI-16.1 test 2 points back to. This settles, at the architecture level, that Layer 1 does **not** ship an accumulation/reconstruction API as its own production surface — accumulation is a Layer 2 (or at minimum consumer-side) responsibility, and Layer 1's obligation is only that the fragments, concatenated in order, are byte-exact. AI-16.2's charter acceptance line ("Concatenated deltas reconstruct the text byte-exactly") is therefore a **property Layer 1's own tests must prove**, not necessarily a public helper Layer 1 ships.

## Approaches

1. **Three new event-kind payloads registered into AI-14's envelope, each carrying an explicit block index; delta fragment stored as a raw string with no text-content validation reused from `textPayload`.**
   - Pros: Directly mirrors the house style already proven at AI-06 (closed vocabulary, registry table, exhaustiveness guard, one-file-per-kind, sealed opaque payloads). Keeps "kind derived from payload" intact (AI-14.1 test 1) since each of start/delta/end is its own registered kind rather than one kind with an internal sub-discriminator. Delta fragments stay byte-exact for free by reusing the "store the string, validate nothing about its encoding" posture `text_content.go` already established and documented.
   - Cons: Three new kinds to register (more registry-table surface than a single "text event" type) and a coupling edit into AI-14's guard file that AI-16 does not own.
   - Effort: Medium — mostly mechanical once AI-14's registry shape exists, since the pattern to copy is fully worked out in `content_part.go`.

2. **A single `TextEvent` payload type carrying an internal phase enum (start/delta/end) instead of three registered kinds.**
   - Pros: Fewer registry entries; one file.
   - Cons: Violates AI-14.1 test 1 ("kind is derived from that payload — a caller cannot set a kind that disagrees with what the event carries") in spirit if the phase is a settable field rather than the sole discriminator, and reintroduces exactly the "discriminator and payload can disagree" shape AI-06's file comment calls out as the retired design's defect C1/C2 pattern one level up (an internal enum a caller could mis-set is a second, nested vocabulary problem). Also complicates the exhaustiveness guard, which is built to compare declared constants against a registry table — a sub-enum inside one kind is invisible to that machinery.
   - Effort: Low to build, but fights the codebase's stated invariants rather than extending them — not recommended.

3. **Reuse `Part`/`PartKindText` directly as the event payload — wrap a `Part` per delta.**
   - Pros: Zero new vocabulary; text-events "are" text content parts.
   - Cons: Breaks immediately on AI-16.3 and on any whitespace-only or zero-length delta fragment, because `NewText`'s `ErrEmpty` rule (`strings.TrimSpace == ""`) is a content-part rule about a *complete, model-visible* value, not a streamed fragment. A `Part` is also documented as a complete, immutable value constructed once (V-REQ-06 byte-equal payload); reusing it per-delta conflates "a finished message's content unit" with "an in-flight fragment of one," which are different lifecycles with different validity rules. Rejected.

## Recommendation

**Approach 1.** It is the only option that extends the already-proven closed-vocabulary/registry/guard pattern rather than working around or fighting it, and it is the only option that survives AI-16.3 (zero-delta blocks) and the multi-byte-rune-split test without inventing an exception to an existing content-part rule. Concretely for the propose/design phases:

- Each of text-block-start, text-delta, text-block-end becomes its own registered event kind (mirroring `PartKindText`, `PartKindReasoning`, etc.), each carrying an explicit block-index field stamped by the producer (not derived), following AI-14.2's per-stream-sequence precedent rather than `tool_call.go`'s derived-ordinal precedent.
- The delta fragment is stored as a plain string (or `[]byte`, TBD in design), returned byte-for-byte, with **no** reuse of `textPayload.validate`'s emptiness/whitespace rule — a delta fragment's only rule, if any, should be a documented "no rule" or, at most, a bound mirroring `MaxTextLen` for defense against runaway payloads (open question below).
- Layer 1 ships **no public accumulation/reconstruction helper** as production API — AI-16's own tests prove byte-exact concatenation and the multi-byte-rune-split case with a test-local helper, consistent with doc 0001 § 4.3 invariant 1 ("consumers accumulate") and the Layer boundary (`doc.go`: transcript/message reconstruction is explicitly not Layer 1's).
- Filenames: given start/delta/end are one milestone's one deliverable ("indexed text block events") rather than three independently-evolving kinds, either a single `text_events.go` covering the family or three files (`text_block_start.go`, `text_delta.go`, `text_block_end.go`) matching the strict "one file, one kind" rule are both defensible against current precedent; leave as an sdd-design decision once AI-14's actual event-payload file layout is visible to copy.

## Open Questions

1. **Is the block index scoped per-stream globally across all content families, or per-family (text blocks numbered 0,1,2… independently of interleaved reasoning/tool-call blocks)?** The charter only proves this within AI-16 (two text blocks distinguishable by index alone); real transcripts interleave text, reasoning (AI-17) and tool-call (AI-18) blocks. This is a shared-contract question across the three parallel siblings and should be settled once, not independently three times — recommend surfacing it explicitly in the AI-16 proposal/design and cross-referencing AI-17/AI-18 rather than deciding it unilaterally inside one milestone's SDD cycle.
2. **Is a zero-length delta fragment legal?** Charter requires zero *deltas* to be legal (AI-16.3) but says nothing about a delta event that carries zero bytes. Recommend allowing it (no invented constraint) rather than adding an arbitrary non-empty rule the charter never asked for.
3. **Exact Go shape of AI-14's `Event`/kind registry is unknown** since AI-14 is unbuilt. AI-16's own spec/design work can proceed on the charter and this exploration's inferred shape now, but must be re-verified against AI-14's and AI-15's actual landed code before AI-16's apply phase starts, per the orchestrator's own note that apply is sequenced after AI-15 lands.
4. **Does AI-16 need its own exhaustiveness-guard-style coupling test**, mirroring AI-06.4, scoped to the text-event family, or does AI-14's own guard (if it enumerates all event kinds package-wide) already cover it? Depends entirely on AI-14's landed shape.

## Risks

- **Sequencing risk (structural, not this exploration's to fix):** AI-16 depends transitively on both AI-14 and AI-15, neither of which is on disk. Propose/spec/design can proceed against the charter, but any concrete Go signatures drafted now are provisional and will need a fast re-check once AI-14/AI-15 land, or the design risks drifting from the actual registry shape.
- **Cross-milestone coupling risk:** the block-index scoping question (Open Question 1) is genuinely shared with AI-17 and AI-18. If each of the three parallel SDD cycles answers it independently, the risk is three incompatible numbering schemes landing in three separate PRs that all pass their own tests and only reveal the mismatch when Layer 2 tries to consume mixed-content streams.
- **House-style violation risk:** reusing `textPayload.validate`'s emptiness rule for delta fragments (Approach 3, or a careless version of Approach 1) is the most likely way to silently reintroduce a bug class the AI-06 exploration already fought (C1/C2-style rule reuse in the wrong place) — flagging explicitly so sdd-design and sdd-spec don't default to "just call the existing text validator."
- **Tooling gap in this exploration run:** `mem_search`/`mem_get_observation` were unavailable to this executor, so the requested `learning/sdd-rework-patterns` and `learning/sdd-spec-inconsistency-patterns` Engram lookups could not be performed. The AI-06 content lookup was substituted with direct source reads (equivalent or better), but the two pattern-learning lookups were not substitutable and should be re-attempted by a phase agent that has `mem_search` available (e.g. sdd-propose) before finalizing the proposal.
- **Persistence gap in this exploration run:** this executor's tool list did not include a file-write tool, so `openspec/changes/cachicamas-ai-text-events/explore.md` was not created on disk despite hybrid mode requiring it.
